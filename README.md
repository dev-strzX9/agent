# 반도체 MES 조회 에이전트 (하이브리드)

장비 상태, 랏(lot) 위치/상태, 계측(metrology) 결과, 공정별 가용 장비를
자연어로 조회하는 랭그래프(LangGraph) 기반 에이전트입니다.

**약한 LLM(GLM 낮은 버전 등) 환경을 전제로 설계된 하이브리드 구조**입니다.
LLM에게는 쉬운 일(분류, 요약)만 시키고, 틀리기 쉬운 판단(툴 선택, 체이닝,
팬아웃)은 파이썬 코드가 수행합니다.

## 동작 구조

```
                 START
                   │
                   ▼
              extract  ──  LLM 1회: 태스크 분류 + 파라미터 추출 + DB 검증
                   │
        분류 성공  │  분류 실패 (UNKNOWN / 파싱 깨짐)
       ┌───────────┴─────────────────────┐
       ▼                                 ▼
   scenarios                        react_agent ◄──┐
   시나리오 함수 실행                    │         │
   (체이닝/팬아웃은 코드가,              │ tool_calls 있음
    태스크 여러 개면 병렬)               ▼         │
       │                            react_tools ───┘
       ▼                                 │
   summarize ── LLM 1회: 결과 요약       │ tool_calls 없음
       │                                 ▼
       ▼                                END
      END
```

- **주 경로 (왼쪽)**: 자주 나오는 질문 유형은 LLM 호출 딱 2회(분류 + 요약)로
  처리됩니다. "장비 조회 → 결과에서 랏 ID 꺼내기 → 랏 N개 조회" 같은
  체이닝/팬아웃은 시나리오 함수(파이썬)가 수행하므로 모델 성능과 무관하게 정확합니다.
- **폴백 (오른쪽)**: 카탈로그에 없는 새로운 유형의 질문만 ReAct 루프
  (LLM이 툴을 골라가며 시도)로 처리됩니다. 폴백으로 자주 빠지는 유형이
  보이면 시나리오로 "승격"시켜 주 경로를 넓혀갑니다.

## 실행 방법

```bash
cd agent
pip install -r requirements.txt

# OpenAI 호환 API 접속 정보
export LLM_API_KEY="..."
# export LLM_API_BASE="http://localhost:11434/v1"   # 사내 서버/Ollama 등
# export LLM_MODEL="glm-4-..."
# export PARALLEL_TOOL_CALLS=1   # 강한 모델이면 ReAct 병렬 툴 호출 허용

python main.py
```

## 파일 구조 (읽는 순서 추천)

| 순서 | 파일 | 역할 |
|---|---|---|
| 1 | `config.py` | 환경 변수, 턴 수 상한, 병렬 툴 호출 스위치 |
| 2 | `tools/mes_mock.py` | 가짜 MES 데이터 계층. **실서버 전환 시 이 파일만 교체** |
| 3 | `tools/definitions.py` | 툴 스키마 + 구현 + 레지스트리 (시나리오와 ReAct가 공용) |
| 4 | `tasks/scenarios.py` | **주 경로의 본체.** 시나리오 함수(체이닝/팬아웃) + 레지스트리 |
| 5 | `tasks/extraction.py` | LLM 태스크 추출 + DB 엔티티 검증 + 라우팅 결정 |
| 6 | `llm_client.py` | requests로 OpenAI 호환 API 직접 호출 (SDK 없음) |
| 7 | `state.py` | 그래프 공유 상태 정의 |
| 8 | `graph.py` | **전체 조립.** extract → scenarios/react 분기를 랭그래프로 정의 |
| 9 | `main.py` | 대화형 CLI + ReAct 폴백용 few-shot 시스템 프롬프트 |

## 핵심 설계 결정

**태스크의 단위는 "함수 호출"이 아니라 "추적 경로"**
"장비가 최근 진행한 5개 랏의 현재 위치"에서 랏 ID들은 질문에 없고,
1차 조회(장비) 결과 안에서 실행 중에 생겨나는 파생 값입니다. 태스크를
함수 호출 단위로 쪼개면 `$t1.result.recent_lot_ids` 같은 바인딩 문법이
필요해지므로(= DAG 엔진을 직접 만들게 됨), 파생 값이 생기고 소비되는
구간 전체를 시나리오 하나로 묶습니다. 태스크 파라미터에는 질문에서 바로
채울 수 있는 값만 남습니다:

```json
{"task": "TRACE_RECENT_LOTS", "params": {"eqp_id": "4EKE0201", "limit": 5}}
```

**LLM이 뽑은 값은 항상 코드가 검증**
장비/랏 ID는 DB 존재 확인(환각/오타 필터), 숫자는 범위 클램프,
스키마에 없는 파라미터는 제거. 검증 실패는 폴백이 아니라 "해당 장비
없음 + 전체 목록 힌트"라는 정상 답변으로 처리됩니다.

**다중 질문 = 태스크 배열**
"장비 상태랑 홀드 랏도 보여줘" → 태스크 2건 추출 → 코드가 병렬 실행 →
요약 LLM이 통합 답변. ReAct의 병렬 툴 호출보다 약한 모델에게 훨씬 쉽습니다.

## 제공 시나리오 (주 경로)

| 태스크 | 용도 | 내부 동작 |
|---|---|---|
| `EQUIPMENT_STATUS` | 장비 상태 조회 | 단일 조회 |
| `LOT_STATUS` | 랏 위치/상태 + 계측 | 체이닝 (랏 → 계측) |
| `TRACE_RECENT_LOTS` | 장비의 최근 랏 N개 위치 추적 | 체이닝 + 팬아웃 (장비 → 랏 N개 병렬) |
| `DIAGNOSE_HOLD` | 랏 홀드 원인 진단 | 체이닝 (랏 → 계측 FAIL 추출) |
| `FIND_CAPABLE_EQUIPMENT` | 공정별 가용 장비 | 단일 조회 |
| `LIST_HOLD_LOTS` | 홀드 랏 전체 목록 | 단일 조회 |

새 시나리오 추가는 `tasks/scenarios.py`에서 함수 작성 + 레지스트리 등록
2단계면 끝납니다. 태스크 추출 프롬프트는 레지스트리에서 자동 생성되므로
다른 파일은 수정할 필요 없습니다.

## 예시 질문

- `EQP-PHO-01 상태 알려줘` — 주 경로 (단일)
- `EQP-MET-01이 최근에 진행한 2개 랏의 현재 위치 알려줘` — 주 경로 (체이닝+팬아웃)
- `EQP-ETC-01 상태랑 홀드된 랏 전부 보여줘` — 주 경로 (다중 태스크)
- `LOT-B001이 왜 홀드됐어?` — 주 경로 (홀드 진단)
- `PHOTO 진행중인 랏 중에 수량 24매짜리만` — 카탈로그 밖 → ReAct 폴백

## 실서버 연동 시 할 일

1. `tools/mes_mock.py`의 `fetch_*` 함수 내부를 실제 MES API 호출로 교체
2. 응답 필드를 현재 dict 구조에 맞게 정규화 (필드명 유지 권장)
3. 운영 로그에서 ReAct 폴백으로 빠지는 질문 유형을 모니터링하고,
   반복되는 유형은 시나리오로 승격

주의: 향후 장비 홀드/랏 릴리즈 같은 **쓰기 작업**을 추가할 때는
반드시 실행 전 사용자 확인(human-in-the-loop) 단계를 넣을 것.
랭그래프의 `interrupt` 기능을 사용하면 됩니다.
